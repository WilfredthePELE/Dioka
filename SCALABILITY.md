# Dioka capacity review — 20 October 2026

## Status
The application has been hardened and the live Supabase schema upgraded. **10,000 simultaneous production buyers are not capacity-certified.** The Supabase organization is currently Free and the Truehost server type/resources have not been verified. Real server credentials, Stripe and Google configuration remain owner-supplied; the local preview deliberately uses SQLite with payments disabled. No paid infrastructure or live website deployment was performed.

## Changes
- Replaced store-wide account, inventory, order, chat and subscriber JSON updates with independent records and indexed lookups. Existing snapshots are preserved for recovery.
- Stock reservations and releases use short PostgreSQL transactions, ordered row locks and provider-independent reservation IDs. Concurrent requests cannot silently oversell. Price and inventory remain server-authoritative.
- Checkout attempts persist a stable idempotency key and exact payment request. An ambiguous provider timeout retains stock and retries the same checkout; it does not create another charge or restore potentially sold inventory.
- Global checkout admission defaults to 20 attempts/second, returns a retry delay and preserves the bag. This is rate admission with client retry, not a durable FIFO waiting room. Quotas must be chosen for the actual Stripe account and measured backend.
- Public catalogue/content responses have short CDN cache headers, ETags and coalesced reads. Private account, order and chat responses are not publicly cached. Inventory shown in a cache is advisory; the checkout transaction is authoritative.
- Request bodies are bounded while streaming. Password hashing has a bounded in-flight budget. Scale mode rejects a local-only persistence configuration.
- Website controls expose 383 registered text/media/link/section fields, policy text, section visibility and ordering, alongside catalogue, stock, media, messages, subscriptions and order status. Links are validated; arbitrary scripts cannot be injected through the editor.

## Verification
The isolated PostgreSQL correctness model processed 10,000 attempts against 5,000 units: 5,000 accepted, 5,000 rejected, zero overselling. Its single-engine execution is not a concurrency capacity benchmark. The local HTTP run completed 10,000 requests with at most 100 in flight: 5,000 HTTP 200, 5,000 sold-out HTTP 400, zero unexpected 5xx, zero remaining units; elapsed 187.81 seconds, p50 1,716.91 ms, p95 2,976.47 ms, p99 3,271.75 ms. This used one local Node process, SQLite and a deterministic Stripe fixture, with test admission raised to 1,000/second. It does not measure real payment/network/Supabase capacity or 10,000 simultaneous users. A separate test sent 100 overlapping purchases for 37 units and verified exactly 37 acceptances, plus idempotent retry and ambiguous-provider-timeout recovery. The production build and standalone type check passed. All 15 integration groups passed, including desktop/mobile browser workflows, owner/customer authorization, product/content publishing, private two-way chat, Google OAuth safeguards, signed payment fulfillment, retry recovery and restart persistence. Browser screenshots initially timed out under local load; a separate rerun with a longer capture timeout passed.
Live Supabase verification preserved the owner account and 12 zero-stock products; reserve/sold-out/idempotent-release checks ran inside a rolled-back transaction. Browser roles cannot execute stock functions, and RLS remains enabled. Advisors reported only informational notices: intentional server-only tables have [no browser policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy); new [unused indexes](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index) should be evaluated after representative traffic.

## Requirements before a 10,000-person launch
1. Deploy the Node application behind a CDN/WAF and trusted load balancer that overwrites forwarded client headers. Set DIOKA_SCALE_MODE=true, DIOKA_TRUST_PROXY=true, and shared Supabase server credentials. Multiple app instances must share Supabase; SQLite is for a single durable server or local preview.
2. Select Supabase compute and storage from measured CPU, IO, lock waits and API latency. Free capacity is not an assurance for this launch. See [compute guidance](https://supabase.com/docs/guides/platform/compute-and-disk). The app uses the Data API; 10,000 shoppers should not mean 10,000 direct PostgreSQL connections.
3. Put a managed waiting room or queue ahead of the checkout path for a synchronized drop. Confirm [Stripe rate and concurrency limits](https://docs.stripe.com/rate-limits); never raise app admission to 10,000 requests/second merely because 10,000 people are visiting.
4. Use a staging deployment with equivalent compute, separate test database and Stripe sandbox. Ramp 100 → 1,000 → 5,000 → 10,000 concurrent shoppers; test browsing, sign-in, carts, concentrated hot-product checkout, retries, webhooks and admin work together. Inject database/provider timeouts and restart an instance mid-checkout. Do not run destructive tests against real orders or live cards.
5. Require zero overselling and duplicate orders; no lost paid orders; explainable sold-out/queue responses; agreed latency/error budgets (proposed admitted checkout p95 under 3 seconds, unexpected 5xx below 0.1%); healthy database CPU/IO/locks and bounded app memory throughout a sustained soak. Queue wait is a separate metric from admitted checkout time.
6. Configure monitoring, alerts, verified webhook delivery/retries, backups and a restore drill. Schedule the server-only dioka_cleanup_temporary(1000) RPC every minute, in bounded repeat batches if needed, for expired session/OAuth/rate records. It never removes payment history or stock reservations.

## Operational limits still requiring attention
- Owner payment checks review the latest 10 stored checkouts and only release stock when Stripe confirms expiry. Unknown provider results retain stock. An interrupted checkout with no stored Stripe session requires retrying its original idempotency key or manual provider reconciliation; never blindly release it by time alone. Older pending payments need a background reconciliation worker before a large launch.
- Admin overview totals cover all records, while order, conversation and subscriber lists show the latest 100. Full historical pagination/export and bulk workflows remain a follow-up for high-volume operation. Product listing is bounded at 1,000.
- Chat currently uses polling. Large numbers of active chat windows should move to authenticated push delivery or adaptive polling and be included in the mixed workload test.
- Currency, allowed shipping countries, payment keys, authorization rules and custom page code remain deployment/developer configuration. The website editor is broad content control, not an unrestricted page/code builder.

## Reproduce local checks
Use Node 22.13+ (Node 24 was used): npm ci, npm run build, npm run typecheck, npm run test:integration. For the local 10,000-request fixture set DIOKA_RUN_LOAD=1 before integration; maximum in-flight requests is 100. Set DIOKA_BROWSER_PACKAGE to an installed Playwright module and DIOKA_BROWSER_CHANNEL=chrome for browser checks. No real payment keys are used by the fixtures.

The Supabase CLI download did not complete in this environment. The verified SQL was applied using the connected Supabase migration tool; its generated version 20261020093827 is mirrored in supabase/migrations, rather than inventing a local migration version.
